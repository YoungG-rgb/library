# Стандарты разработки

Каталог содержит правила «как делать X» для агентов и людей, работающих в любом backend-проекте на Spring Boot + JPA. Стандарты — imperative, бьются по узким темам, без воды.

## Когда использовать

- Перед созданием новой сущности / репозитория / сервиса — открой соответствующий файл.
- При код-ревью — ссылайся на правила из стандартов вместо переписывания обоснований.
- При расхождении со стандартом — либо обнови код, либо обнови стандарт (с обоснованием в PR-описании).

## Приоритет: сначала стандарт, потом «как обычно делают»

- Перед тем как писать конфиг/боилерплейт **любого** вида (профили `application.yml`,
  структура `pom.xml`, security-конфиг, DI-конструктор) — сначала открой файл стандарта
  по теме, потом пиши код. Не воспроизводи «типовой Spring Boot паттерн из общих знаний»
  (например `application-{env}.yml`, `@Autowired` на полях, конструктор руками) без
  сверки с этим каталогом — если он здесь описан иначе, здесь и есть источник правды
  **для этого проекта**, даже если где-то ещё принято по-другому.
  - **Почему:** несколько раз в этом проекте типовой, общеизвестный Spring Boot паттерн
    побеждал уже написанный здесь стандарт просто потому, что стандарт не перечитывали
    заново в момент правки конкретного файла (пример: `application-prod.yml` при том,
    что `application-config.md` явно требует профиль-по-концерну, не по окружению).
  - Если стандарт кажется неприменимым к конкретному случаю — не отступай молча;
    либо обнови сам стандарт (с обоснованием), либо явно спроси/зафиксируй отступление
    в ADR/задаче. Молчаливое расхождение — то, что превращает стандарт в необязательную бумагу.
- Для нового проекта см. корневой `CLAUDE.md` — он обязан явно указывать «читать
  `.claude/standards/` перед первым коммитом инфраструктурного кода» с чек-листом
  обязательных зависимостей, которые стандарты подразумевают (Lombok и т.п.).

## Правила ведения

- Стандарт = один файл = одна тема. Не сваливай всё в общий.
- Формат: короткие правила в bullet-форме, императив (`Делай X`, не «можно делать X»).
- Если в правиле есть «почему» — добавляй в формате `**Почему:**` после правила (одна-две строки).
- Примеры — только если правило неочевидное. `// ОК` / `// ПЛОХО` рядом.
- Не привязывай стандарт к конкретному проекту: не используй реальные имена пакетов, таблиц, файлов. Только обобщённые placeholder'ы (`OrderEntity`, `UserEntity`, `...services`).
- Стандарт не заменяет проектные конвенции (CLAUDE.md, AGENTS.md и т.п.) — они дополняют его проектной спецификой.
